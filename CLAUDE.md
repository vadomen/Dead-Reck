# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DriveLogger (working name) is an iPhone app that records in-car sensor logs — OBD-II
over Bluetooth, CoreMotion, CoreLocation — for offline dead-reckoning research.
The app's job is capture fidelity, not navigation: nothing is computed live that
could be computed later from a recording.

iOS 17+, iPhone only, portrait. SwiftUI app lifecycle, Swift 6 language mode with
strict concurrency.

## Toolchain note

`xcode-select -p` on this machine points at `/Library/Developer/CommandLineTools`,
which cannot build iOS targets and cannot load the Swift Testing macro plugin
(`swift test` fails with "plugin for module 'TestingMacros' not found").

Either fix it once:

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

or prefix the commands below with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.
Every command in this file assumes Xcode is the active developer directory.

## Commands

Test Core on the Mac — no simulator, no signing, the fast inner loop:

```bash
cd Core && swift test
```

Run one Core test or suite. `--filter` matches `SuiteType/functionName`, not the
`@Test("…")` display name (a display name runs zero tests, with only a
"No matching test cases were run" warning):

```bash
cd Core && swift test --filter OBDDecoderTests/decodesEngineSpeed
cd Core && swift test --filter OBDDecoderTests
```

Build the app for the simulator:

```bash
xcodebuild -project DriveLogger.xcodeproj -scheme DriveLogger \
  -destination 'generic/platform=iOS Simulator' build
```

Run the app tests. `generic/platform=iOS Simulator` builds but cannot run, so
testing needs a concrete device. Match by `id=`, not `name=` — name matching
fails against some installed runtimes and xcodebuild then falls back to macOS and
reports a confusing destination error:

```bash
xcrun simctl list devices available | grep iPhone
xcodebuild -project DriveLogger.xcodeproj -scheme DriveLogger \
  -destination 'platform=iOS Simulator,id=<UDID>' test
```

Compile the test target without running it:

```bash
xcodebuild -project DriveLogger.xcodeproj -scheme DriveLogger \
  -destination 'generic/platform=iOS Simulator' build-for-testing
```

Regenerate the project:

```bash
xcodegen generate
```

## Project generation

`project.yml` is the source of truth. Never edit `DriveLogger.xcodeproj` directly —
it is regenerated and your change will be lost.

**Run `xcodegen generate` after adding or removing any file.** XcodeGen expands
the `sources` globs at generation time, so a new file is invisible to the Xcode
build until the project is regenerated. `swift test` picks up new Core files
without it, which makes this easy to forget: Core tests go green while the app
target still doesn't see the file.

The `.xcodeproj` is committed so a fresh clone opens in Xcode without running
XcodeGen first. Commit the regenerated project along with the change that caused
it.

Two settings are easy to get wrong here:

- `TARGETED_DEVICE_FAMILY` must be set **per target**. XcodeGen writes a default
  of `"1,2"` onto every iOS target, which overrides a project-level value and
  silently produces an iPad-capable build.
- `Info.plist` is hand-maintained and referenced via `INFOPLIST_FILE`, with
  `GENERATE_INFOPLIST_FILE: NO`. Edit the plist directly; `xcodegen generate`
  leaves it alone.

## Signing

`Config/Signing.xcconfig` is committed and holds no secrets. It ends with
`#include? "Local.xcconfig"`, so the git-ignored `Config/Local.xcconfig` wins
where it overlaps. Device builds need it:

```bash
cp Config/Local.xcconfig.example Config/Local.xcconfig
```

Simulator builds and `swift test` work without it — they are deliberately
unsigned, so the project builds on a machine with no signing identity.

**A team ID goes in `Config/Local.xcconfig` and nowhere else.** Not in
`project.yml`, not in `Signing.xcconfig`, not in the generated `.xcodeproj`.

## Invariants

These are the properties that make recorded drives worth keeping. Breaking one
silently corrupts research data, which is why each has tests guarding it.

### Core imports no Apple UI or hardware frameworks

`DriveLoggerCore` may import `Foundation` and nothing else from Apple.
No `UIKit`, `SwiftUI`, `CoreBluetooth`, `CoreMotion`, `CoreLocation`, `MapKit`.
That is what keeps `swift test` runnable on a Mac in seconds with no simulator,
and it is the whole reason the parsing and format logic is testable at all.

The app layer talks to the hardware and converts into Core's types at the
boundary — `MotionSample`, `LocationSample`, `OBDSample` mirror the CoreMotion and
CoreLocation shapes field for field so that conversion stays mechanical.

Check with:

```bash
grep -rhoE '^[[:space:]]*import[[:space:]]+[A-Za-z_]+' Core/Sources Core/Tests | sort -u
```

### All sensor timestamps come from one monotonic clock

Every sample in a recording is stamped with a `MonotonicTimestamp` from the
session's single `SessionClock`. Construct exactly one per recording and hand it
to every sensor adapter.

- The time base is seconds since boot, as supplied by `UptimeSource`, which must
  match the base CoreMotion uses for `CMLogItem.timestamp`. CoreMotion is the
  highest-rate stream and the only one that delivers pre-dated buffered samples,
  so everything else converts *into* its clock.
- Streams that carry their own uptime use `clock.timestamp(uptimeSeconds:)`.
  Streams that don't — an OBD reply arriving over Bluetooth — use `clock.now()`.
- Wall-clock time is captured **once**, in the log header. Never call `Date()`
  per sample. `SessionClock.wallClock(for:)` exists for display and export only;
  it inherits every NTP correction and time-zone change from the drive.
- Negative offsets are legal and must not be clamped: a CoreMotion batch can
  begin before the session did, and clamping collapses distinct samples onto one
  timestamp.

### Recordings are never committed

`.gitignore` covers `*.jsonl`, `*.jsonl.gz` and `logs/`. A recording is large,
pointless to diff, and a precise record of where someone drove and when — and git
history is the wrong place for something you may need to delete. If you need a
sample for a test, hand-write a minimal fixture in the test file (see
`LogFormatCompatibilityTests`), don't check in a real drive.

### The log format is versioned, and old versions stay readable

Format is JSON Lines: a `LogHeader` first, then one `LogEvent` per line.
Append-only, so a recorder can flush per line and a reader can stream a
multi-hundred-megabyte drive.

- `LogFormatVersion.current` is what new recordings are written in.
- **Every version ever written must stay decodable.** Adding a version means
  adding a case, bumping `current`, and extending `LogCodec` — never repurposing
  or removing an existing field.
- `LogFormatCompatibilityTests` holds a frozen v1 recording. It must never be
  edited to accommodate a format change. If a change breaks it, either the change
  is wrong or it needs a new version plus a migration that leaves the fixture
  passing. Add a fixture per version.
- On-disk strings are part of the format: `LogEventKind` raw values, `OBDUnit`
  raw values, `OBDPID` raw numbers, and the `t`/`kind`/`data` keys. Rename the
  Swift case if you like; never the string.
- Unknown event kinds decode to `LogEvent.Payload.unrecognized` with their
  payload preserved in a `JSONValue`, so an older build reading a newer file
  doesn't destroy data on re-export. A newer *header* version is refused
  outright — guessing would produce plausible but wrong data.
- `LogCodec` encodes with sorted keys and ISO 8601 dates, so output is
  byte-stable. Tests depend on that.
- `LogRecovery.skipMalformedLines` exists because a drive that ends in a flat
  battery leaves a half-written final line; losing one sample beats losing the
  drive.

## Conventions

- Swift Testing (`@Suite`/`@Test`/`#expect`), not XCTest, in both test targets.
- `LogCodec` is deliberately not `Sendable` — it owns a `JSONEncoder`/`JSONDecoder`
  pair. Keep one per reader or writer, inside whatever actor owns the file handle.
- ELM327 adapter status strings (`NO DATA`, `UNABLE TO CONNECT`) are protocol,
  not transport noise. `NO DATA` is the normal answer for a PID a vehicle doesn't
  implement; record it and stop polling that PID rather than retrying forever.
- When splitting adapter text on line endings, split the **unicode scalar** view.
  Swift treats `\r\n` as a single `Character`, so a `Character`-level separator
  never matches it and lines come back with `\r\n` still attached.
